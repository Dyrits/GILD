## CHG-0271 · 2026-11-13 · Realm archive, recovery, and the Realms overview

## CHG-0273 · 2026-11-14 · A workspace's own git worktrees count as its folder (widens the sandbox's writable area)

Type: Code
Event: Agreement and Delivery
Scope: Action approval, Claude Code sandbox, thread instructions

Summary: Threads in the Iskios realm kept asking on ordinary work. The cause, from the app's own approval history (aggregate counts, nothing copied): the default level worked (61 harness actions ran unasked), but the 36 questions asked on 2026-11-14 came from threads working in git worktrees beside the checkout (`../ISKIOS-<branch>`), which lie outside the thread's folder: Claude Code's sandbox writes only that folder, so each command there was an escape question (22 "Run outside the sandbox") and each edit one outside the workspace (14), and Always allow, which saves an exact command, could not help. The linked worktrees git lists for a workspace's repository now count as the thread's folder: Claude Code's sandbox writes them and the edit check counts files in them as inside. Only those worktrees, re-read at each start and at each edit, each checked by real path; none for another repository's, an unrelated sibling folder, a thread's own copy, a subfolder, or a thread folder that is a link. The thread instructions now tell a thread not to escape for work in its folder or worktrees, and to make worktrees as `.worktrees/<name>` (git-ignored) or in `$TMPDIR`. Git over SSH, other projects' folders, and signalling processes still ask. **For the owner to review: this widens what a sandboxed Claude Code thread may write.**
Reason: At the default level only sensitive actions should ask (CHG-0208); the repository's own workflow commits on a worktree branch, so ordinary work was asking.
References: [action-approval specification](../capabilities/action-approval/specifications.md), CHG-0208, `packages/service/src/harness/worktrees.ts`.
Validation: Test first. Red, then green: `worktrees.test.ts` (listing, missing, link, own copy, subfolder, other repository), `containment.test.ts`, `approvals.test.ts` (a worktree edit unasked; an unrelated sibling, another repository's worktree, and a worktree replaced by a link asked), `claude.test.ts` (sandbox writes exactly the caches and the listed worktree; restart when one is added), `instructions.test.ts`. Green after: `bun run check` and `bun run typecheck` clean; the whole service suite passes (854 tests) except 24 Seatbelt-dependent OpenCode tests that cannot run inside the agent's own sandbox (nested `sandbox-exec` refused), which pass (109 tests) when run outside it. Not checked: a live Claude Code run in a worktree (only the stand-in process), Codex and OpenCode sandboxes (unchanged), and the owner's window.

## CHG-0277 · 2026-11-14 · A sandboxed OpenCode no longer sees other processes

Type: Code
Summary: Audit SA-11 and SA-13, checked with dummy tokens and stand-in processes. Under OpenCode's Seatbelt profile, a sandboxed command could list every process, map a port to one, and read the arguments and environment of any of them. That included the service's owner token and every other thread's tool server address, Claude Code threads' included. The profile now denies `process-info*` except within its own sandbox, and denies `sysctl-read` of `kern.procargs*`. Without the second rule, a process named by its pid stayed readable. Its own children stay readable, and `node`, `git`, `python3` and OpenCode run as before. Claude Code's and Codex's profiles already allow process information only within their own sandbox; this was read, not run. Threads keep sharing context through the thread tools, which never used the process table.
Reason: Any OpenCode thread could act as the owner or as another thread, whatever the approvals said.
References: [verification](../verification/2026-11-14-token-isolation.md), [action-approval specification](../capabilities/action-approval/specifications.md), [security audit run 2](../security-audit/security-audit-2026-11-14-0233.md), `packages/service/src/harness/openCodeSandbox.ts`.
Validation: Test first in `openCodeSandbox.test.ts`: the profile's rules and their order, and a macOS run in which the outside control reads the stand-in, the sandboxed reader does not, and the sandbox's own child stays readable. Both failed before the fix. Typecheck, Biome and the whole suite passed (1539 passed, 14 skipped). Not checked: a live OpenCode turn, Linux, and a run under Claude Code's or Codex's sandbox (the session's permission classifier declined it).

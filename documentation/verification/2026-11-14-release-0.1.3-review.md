## Specifications

The coordinating agent checked the cited source paths against the checkout. These were behavior findings, not refactors; each is now fixed red/green in CHG-0280 (see [Behavior fixes](#behavior-fixes-chg-0280)). The analysis below is kept as found. Review priorities are not a claim of a newly executed security audit. The independent Specifications verification confirmed that the refactors preserved agreed behavior, interfaces, and wire contracts, and that all six findings below are still present in the current source.

### SP-01: a mid-turn selection changes the running turn's permission authority

Agreement: [thread handover](../capabilities/thread-handover/specifications.md#agreed-behavior) says the running turn finishes on its admitted runner; only the next turn uses the new selection. CHG-0274 restricts `answer_prompt` to harnesses that use it.

`work/handover.ts` immediately updates `threads.harness`. `work/mcp.ts:66–83` authorizes and lists `answer_prompt` from that mutable row; `work/approvals.ts:307–317` derives containment from it too. Choosing Codex during Claude execution refuses genuine subsequent Claude permission-tool calls; reversing the change exposes the Claude-only tool to a still-running non-Claude turn. The selected next runner and the active executing runner need separate policy identities.

Red/green seam: hold a fake Claude turn, select Codex, then call its authenticated MCP endpoint and assert ordinary prompt handling rather than unavailable-tool refusal. Reverse harnesses and retain refusal. Use differing fake containment reports to test the running turn's policy. Existing handover/session tests do not cover permission calls after a picker change.

### SP-02: a multi-file edit inherits permission for only its first outside file

Agreement: [action approval](../capabilities/action-approval/specifications.md#standing-permissions) limits a standing permission to the exact action/target. CHG-0274 promises multi-file handling.

`harness/openCodePrompts.ts` sends the first outside path as `file_path` and all paths as `file_paths`. Both `policy/patterns.ts` functions `targetOf` and `changedFilesOf` ignore `file_paths`. `work/approvals.ts` can consequently authorize A+B with a standing permission saved for outside file A alone.

The reviewer ran a pure check: A and A+B both produced `Edit /outside/approved`; changedFiles returned only A and permission matching returned true. The coordinator verified the source trace, not that execution.

Red/green seam: extend the stand-in two-file test. Always allow A; request A+B; require a new question before any allow reply; Deny must refuse. Include sets sharing the same first outside path. Carry the complete target set through containment and permission identity.

### SP-03: owner-word path matching still accepts a broader ancestor

Agreement: [mission coordination](../capabilities/mission-coordination/specifications.md#external-contract) says a folder path is not found inside a longer one.

The `phraseOf` matcher in `policy/ownerRequests.ts` rejects a separator only before a limited character class. With action `{ operation: "CreateRealm", targets: ["Garden"], value: "/dummy/root" }`, the reviewer's pure check accepted both `Create realm Garden at /dummy/root//projects/app.` and `Create realm Garden at /dummy/root/😺.` as authority for `/dummy/root`. The ordinary child path is rejected. The coordinator verified the regex/source only.

Red/green seam: extend `ownerRequests.test.ts` with the real name-plus-folder action shape, repeated separators and non-ASCII/punctuation-starting components; add a provenance test requiring a question for the broader folder. Match complete path-valued evidence, not a partial word boundary.

### SP-04: an unmounted composer retains text that was successfully sent

Agreement: CHG-0269 says successful sending forgets saved unsent text.

`ui/controls.tsx:179–188` clears only the mounted editor ref after success. The saved map is updated only through editor onChange. Leaving while a send is pending can make the ref null, leaving the already-sent draft saved; the realm handoff navigates from inside its send handler too.

Source-supported, not renderer/window reproduced. Red/green seam: deferred successful send, unmount, resolve, remount must be empty; rejection preserves text; text newly entered after remount must survive completion of the older send. Clear the store independently and conditionally/versionedly.

### SP-05: the quest-suggestion realm picker omits duplicate-name hints

Agreement: [mission tracking](../capabilities/mission-tracking/specifications.md#realm-names) requires parent-folder hints in realm pickers when active names collide.

Duplicate names are now permitted. Sidebar, overview and RealmChooser use `realms/realmLabels.ts`, but `conversation/suggestions.tsx:178–192` still uses `label: realm.name`. Two realms named `app` are indistinguishable when placing a suggested quest.

Red/green seam: `/client-a/app` and `/client-b/app` both named app must produce different labels and retain correct path selection. Apply the existing shared rule, not a new label convention.

### SP-06: suggestion text can still become structural Owner authority in a Ritual

Agreement: [mission coordination](../capabilities/mission-coordination/specifications.md#external-contract) excludes agent/other-thread text from owner-word authority. Approved [audit SA-06](../security-audit/security-audit-2026-11-14-0233.md#sa-06-thread-written-suggestion-text-becomes-owner-words-and-grants--reach-medium-provisional) covers both mention reach and structural authority.

The changed `work/suggestions.ts:244–249` strips mention-token `@` but retains provenance. Continue inserts `suggestion.text` through `insertUserMessage` with a null sender. Explicit matches may include Rituals. A Ritual is a structural caller for quest actions/settings, and `guildmasterProvenance.ts:72–80` accepts user/null-sender messages except scheduled-run messages, without excluding suggestions.

Residual source-supported path, not an executed integration reproduction or newly introduced exploit. Routing approval must not silently become structural approval. Preserve suggestion provenance and exclude it from owner-word authorization.

Red/green seam: deliver agent-written archive text through Continue to a Ritual with empty reviewed authority; its fake structural tool call must ask, leave the target unchanged before Allow, and preserve it after Deny. Keep legitimate owner requests and reviewed Ritual scope working.

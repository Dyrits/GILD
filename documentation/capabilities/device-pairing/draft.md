# Device pairing: unresolved

Proposals not yet authorized by the owner. Each moves to the [specifications](specifications.md) once agreed.

- **Realm folder picker, build detail**: settled in CHG-0253; see the specifications.
- **Relay hosting risk, from Paseo** (read 2026-11-12): Paseo's production relay is now a separate distributed Elixir service, and its Cloudflare Durable Object relay is kept as "legacy code and is not deployed" ([architecture](https://github.com/getpaseo/paseo/blob/main/docs/architecture.md), [paseo-relay](https://github.com/getpaseo/paseo-relay)). The reason is not stated in what I read. Before relying on a Durable Object relay, find out what Paseo met (limits, cost, connection counts) and measure ours.
- **Other transports, from Paseo**: besides the relay, Paseo connects a client to a daemon directly (the daemon listens on a chosen address, for a LAN or Tailscale, with an optional password) and through an SSH tunnel to an already-running daemon (desktop and CLI). None of them is account-free and reachable from anywhere without the user's setup, so none replaces the shared relay; each could be an optional extra transport later for users who have it.
- **Terminal on a host** (proposed; since batch 2 `!` stays ordinary text while a host is shown, and the notice "available on this computer only" is not written yet): the `!` terminal runs in the desktop's main process, not in the service ([0012](../../architecture-decision-record/0012-desktop-conversation-terminals.md), which says a paired-device terminal needs its own authorization and transport design). The owner wants full control. Proposed staging: its own batch after the channel works, with an amendment to 0012; until then `!` says it is available on this computer only while a host is selected.
- **Host offline** (proposed): a paired device never queues requests for an offline host, so an approval or spending request cannot run hours later; the architecture's queuing of messages for an offline device stays for phone notifications. Needs an amendment to the architecture text.
- **Host menu details** (proposed): beside This computer, the hosts, **Add a host** and **Host settings** (rename, disconnect), leave out OpenBot's "Hide server" and "Server layout".
- **Relay limits and abuse**: read from Cloudflare's pricing page on 2026-11-12: Durable Objects on the free plan allow 100,000 requests and 13,000 GB-s of duration a day (resetting at 00:00 UTC); an incoming WebSocket message counts as 1/20 of a request, an outgoing one is free, and a connection counts as one request; duration is billed at 128 MB of memory only while an object is active and not able to hibernate (it hibernates after 10 idle seconds). So a relay can carry about 2,000,000 incoming messages a day and about 28 hours of active objects a day, summed over all users, and the second limit binds first under steady streaming. These are the account's limits: the owner's other Workers share them. Not measured with real use yet (the Durable Object analytics of the lab run were not yet published). A room still needs a one-time secret and a rate limit; what the host does when the daily limit is reached is open.
- **Lab results, 2026-11-12** (micro project outside the repository, `relay-lab` in the assistant's workspace; nothing in Iskios changed). Option 1, a Worker with a Durable Object per room and hibernating WebSockets, deployed for the test to the owner's account on `workers.dev` and deleted afterwards: host and client connect in about 0.4 s, a 200-byte round trip through it takes about 35 ms from this Mac, a 256 KiB frame about 98 ms, a connection survived 150 idle seconds, and a frame with no host connected is dropped (nothing queued). Option 5, Cloudflare quick tunnels (`cloudflared tunnel --url`): needs no account and no domain, WebSockets work (about 29 ms round trip, survived 90 idle seconds), but the address is new at every start and the old one then answers 530, Cloudflare calls quick tunnels "for testing and development" with no uptime guarantee, and each tunnel takes at most 200 requests in flight ([Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)). It cannot be the default path: a pairing would break at every host restart. Option 4, direct peer-to-peer: from this Mac's network, three STUN servers see the same public port, so hole punching would likely work here; the other side was not tested (mobile networks often differ).
- **Noise library** (settled in batch 1, CHG-0204): `@iskios/channel` ports Paseo's Noise NK (Apache 2.0, attribution in `packages/channel/NOTICE`) on `@noble/curves`, `@noble/ciphers` and `@noble/hashes`; it runs unchanged in Node and in a browser.
- **Own relay** (deferred, [backlog](../../backlog.md)): deploying the same Worker to a user's own Cloudflare account through the temporary-account claim.
- **Direct path upgrade** (proposed 2026-11-12, from two teammate reviews, not yet tried): the relay stays the universal carrier, the place where pairing happens and where the two sides exchange connection offers; the two sides then try a direct WebRTC data channel using public STUN servers and no TURN server, with the same Noise NK session running inside it (DTLS is not the end-to-end layer), and fall back to the relay when it fails. Most sessions would then use almost none of the relay's free daily duration. It is a candidate for a second batch, so the channel in batch 1 should not assume a WebSocket carrier. Lab results of 2026-11-12 (micro project `relay-lab/webrtc` outside the repository, host in Node with the MIT `werift` library, phone in the browser, public STUN, no TURN, signaling through the relay): the host and a second Node peer on one Mac connected directly in 0.2 to 0.4 s and streamed 400 frames at 20 a second with 0 frames through the relay (this crossed no NAT). A phone on 5G (Firefox, Android) connected directly twice, over IPv6 on both ends, in about 0.8 s, received 400 of 400 frames, and the relay carried 0 of them; direct round trips had a median of 60 to 72 ms against 95 to 110 ms through the relay, with one stall of about 1 s each time. A first attempt from a private Firefox tab failed (cause not found). With the host limited to IPv4 so that the path had to cross NAT, a phone on a different Wi-Fi network failed to connect directly in 25 s (it saw two different public IPv4 addresses for its two STUN servers, a mapping that usually blocks direct paths), while this Mac's own network maps one port for all servers; the same IPv4-only test from 5G then succeeded: direct in 0.95 s over IPv4 on both ends (the phone reported both candidates as server-reflexive, so the path crossed the carrier's NAT and the home router's NAT), 400 of 400 frames, 0 frames through the relay, direct round trip median 75 ms against 105 ms through the relay, one stall of about 1 s again. So: with IPv6 on both sides the direct path works and carries the stream; across IPv4 NAT it worked from 5G and failed from one other Wi-Fi network, three direct successes against two failures (one of them a private-tab attempt of unknown cause) over three network setups, a sample far too small for a rate; the relay must stay the fallback. Published evidence: about 70 percent hole-punching success over 4.4 million attempts on 85,000 networks (an IPFS study, arXiv 2510.27500). The test page had a bug (it reported "no STUN answer" because Firefox writes `UDP` in capitals); ignore its NAT verdict line. Unverified: the host's service runs in Node, which has no built-in WebRTC, so a native module or the app window's WebRTC would be needed. Also considered and not taken: iroh (public relays are development and hobby only), libp2p (no public relay infrastructure), Cloudflare's TURN service (reported as paid per gigabyte when used alone, unverified here), a small VPS relay (about €5 a month, worth it only if metered Durable Object use passes about $5 to 10 a month).

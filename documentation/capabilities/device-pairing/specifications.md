# Device pairing

Authorized by the owner on 2026-11-12 (CHG-0201): control one Iskios from another instance of Iskios, from any internet connection, with nothing for the user to set up and no cost to the owner or the users. A phone uses the same pairing later; the phone web app is not part of this first slice. Unsettled points are in the [draft](draft.md).

Terms: the computer being controlled is the **host**; any other Iskios connected to it is a **paired device** ([glossary](../../glossary.md#devices)).

## Behavior

- A paired device reaches its host from any internet connection, through the shared relay ([0016](../../architecture-decision-record/0016-shared-relay-on-the-owners-free-cloudflare-account.md)). The user needs no account with any service and deploys nothing.
- The relay cannot read what it carries: messages between a host and a paired device are end-to-end encrypted, and the keys travel only in the pairing code ([requirements](../../requirements.md#privacy-and-data)).
- A host accepts paired devices only while "Allow paired devices" is on in the Workshop; it is off by default. Turning it off ends every paired device's connection and stops new pairings, and keeps the pairings.
- The host shows a pairing code as text. A code works once and expires 10 minutes after it is shown. The Iskios app on another computer pairs by choosing **Add a host** in its host menu and pasting the code. A QR code of the same code comes with the phone.
- The host lists its paired devices in the Workshop. Each shows its name, its kind (desktop or phone), when it was last active, and a **Disconnect** button. Disconnecting a device ends its connection immediately and forgets its pairing; it can pair again with a new code. A paired device stays paired until it is disconnected.
- A paired device has the owner's full authority over the host: it steers threads, answers approvals, changes budgets and settings, and creates and moves quests exactly as the owner does on the host, except that the folders it may name are limited as below (CHG-0274). Only the host itself shows pairing codes and disconnects devices.
- The host keeps a name, defaulting to the computer's name, and the owner can rename it from the host or from a paired device, in the Workshop's **Computer name** card (Accounts section), no longer in Remote access; the same name labels the computer's own sign-ins (CHG-0257).
- The Iskios app on a computer has a host menu at the top left, like OpenBot's: it lists **This computer** and each paired host, marks the one in use, and switches the whole app to the chosen one, with the same screens and the same abilities as on the host. The data shown is the host's, not the computer's own, and choosing **This computer** returns to its own.
- Choosing a realm folder no longer opens the system dialog, on this computer or on a host. One picker runs on the host: a search field taking typed paths and ranking matches (exact, prefix, substring, then fuzzy; folders only), suggestions from folders the quests already used, step-in browsing through `BrowseFolders`, and a New folder flow (choose the parent, then name it). A search stays inside its root and follows a symlink only if it resolves inside that root; hidden folders, `node_modules`, build output and Git-ignored folders are not offered; a path typed exactly always resolves where the caller may go; at most two filesystem calls run at once, so a stuck drive cannot freeze the host.
- **Where a paired device may look** (CHG-0253, replacing the open root of CHG-0202): only under the host's **browsable roots**, which the host owner sets in the Workshop, in the card "Folders open to Iskios" (they start with the host's home folder; **Add root** and **Remove root**, host only, so a paired device cannot widen its own reach). A typed path, a browse, a search, a suggestion, and New folder outside the roots are refused or left out for a paired device. The same holds for every request that names a folder: starting a quest, creating a Ritual or a realm, listing skills, naming files with `@`, and choosing a realm on a suggestion are refused for a paired device unless the folder lies under a root or is already a realm the host attached (CHG-0274). The host's own window uses the same picker but may reach any folder, as the system dialog did (CHG-0035). Paseo sets no such limit (it searches the host's home folder and resolves any typed absolute path; checked 2026-11-13).
- A host that no longer knows this installation (it disconnected it) refuses it for good: the app stops trying, says "The host no longer knows this computer. Pair with it again.", and offers **Use this computer**; a host that is merely unreachable is tried again, ever more slowly (a second, then doubling to half a minute), because each try asks the relay, whose daily allowance everyone shares.
- While a host is shown, what only works on the computer the window runs on is off, never aimed at the wrong computer: `!` stays ordinary text (the terminal on a host is a later batch); the Workshop's remote access section says that paired devices are managed on the host itself.
- The relay says why it closes a connection, in a text frame sent just before the close (no host, room full, host left, replaced, claim mismatch, a rule broken), and the host and the app act on it at once; the close itself can reach a Node client ten seconds late.
- The owner may use a relay of their own instead of the shared one, never required: the Workshop's Remote access card says which relay is in use, and **Use my own Cloudflare account** deploys the relay to the owner's Cloudflare account with one API token pasted into the app. The card names Cloudflare's token page and the "Edit Cloudflare Workers" template, and says before the token is used what is done: a Worker named `iskios-relay` is put on the account (and a workers.dev address if it has none). The token is used once and kept nowhere. A token that reaches several accounts is refused with the way to limit it to one; a Worker of that name that Iskios did not make is left alone; a failure leaves the relay in use as it was and says why. Once the new relay answers, the host uses it, pairing codes name it, and devices paired through the other relay are disconnected and pair again (their pairings are kept, and work again on returning to the shared relay with **Use the shared relay**); redeploying to update the relay changes nothing for connected devices. Only the host may do this.
- While the host is unreachable, the app says so and reconnects by itself; what the owner does on a paired device reaches the host only while it is connected.

## Acceptance

- Two instances on one computer, each with its own data folder, one acting as host and one as paired device through a locally run relay: pairing with a code succeeds once and a second use of the same code fails; an expired code fails; the paired device shows the host's quests and a message sent from it reaches the host's thread; the host's changes appear on the paired device; Disconnect cuts the connection at once; turning off "Allow paired devices" cuts it too.
- On a paired device, typing a path finds a folder on the host and not on the computer in use; a folder is created on the host; a hidden folder, `node_modules`, and a symlink pointing outside the root are not offered; a typed path to one of them still resolves when it is inside the root.
- The relay's stored messages and logs contain no plaintext (checked by reading what the relay received during the run above).
- The same flow, run once against the deployed relay on the owner's account, from a second network, with the owner's go-ahead before deploying.
- The own relay, with a real token on a test account: a first deployment, a host that moves to it and pairs a second service through it, an update at the same address, the return to the shared relay, a refused Worker of the same name, and the token found nowhere in the host's database (done on 2026-11-12, CHG-0212).
- The free-plan limits of the relay are read from Cloudflare's documentation and measured against a typical session before the first release.

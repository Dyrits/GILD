# The host service runs on its own, and can keep running after the desktop app quits

Agreed with the owner on 2026-11-14 (CHG-0282, CHG-0283); not built. The host service is its own Node program, no longer started only by Electron: the desktop app either connects to a host already running on its data folder or starts one. This meets [Host can outlive the desktop app](../requirements.md#access) and [Same features in every app](../requirements.md#access), and makes Electron an optional shell ([0004](0004-electron-desktop-shell.md)).

- **Runtime**: Node. Desktop builds run the host on the desktop app's own binary as Node (`ELECTRON_RUN_AS_NODE`), so the app still carries one runtime, as Paseo does ([research](../research/paseo-daemon.md)); elsewhere any Node 24. The host uses Effect's runtime-neutral platform services where they exist, so Bun stays possible ([0017](0017-typescript-and-effect-no-rust.md)); a Bun host would first need its own SQLite library ([backlog](../backlog.md)).
- **Lifecycle**: the setting **Keep running after quitting** decides. Off, the desktop app starts the host and stops it when it quits, as today. On, a per-user login service runs the host as the owner (a LaunchAgent on macOS, a systemd user unit on Linux, a startup entry on Windows): it starts at login, comes back after a crash, and stays when the desktop app quits. It runs as the owner because the harnesses use the owner's home folder and sign-ins; while nobody is logged in the host does not run, which the owner accepted. A screen that is off does not stop it.
- **Sleep**: the setting **Keep this computer awake while threads work**, on by default, makes the host hold the system's assertion against idle sleep while any turn runs (what `caffeinate -i` does on macOS, `systemd-inhibit` on Linux, `SetThreadExecutionState` on Windows) and release it when work stops. It cannot prevent sleep when a laptop's lid closes on battery. A sleeping host is unreachable until it wakes.
- **One host per data folder, and local clients**: the host keeps a lock file in its data folder, refreshed while it runs and recognised as stale after it dies, in place of Electron's single-instance lock for this purpose (the lock of [0013](0013-installed-app-apart-from-development.md) still brings the running window forward). At each start it writes its port, chosen at random, and a fresh token to a file only the owner's user can read; the desktop app reads it and hands it to its window as it does today. Any program running as the owner could already read the database itself, so the file exposes nothing new.
- **Paired devices are unaffected**: they prove themselves with the pairing keys the host keeps in its database, never with that token, so a host restart or a new token needs no new pairing code; they reconnect by themselves.
- **Updates**: the host owns the app's updater, moved from the desktop main process, so any app, a browser included, can find, download, and install a release. Installing replaces the installed app and restarts only Iskios, never the computer, and asks for no sign-in: with the setting on, the login service starts the new host; with it off, the desktop app relaunches. A new host that does not start is replaced by the previous version, started again, so an unattended host stays reachable ([Updates keep the host reachable](../requirements.md#releases)). The Windows and Linux updaters, built on `electron-updater`, must be replaced by ones that run without Electron.
- **Packaging**: only the desktop app is released for now; its own binary runs the background host. A standalone host package (an npm package, or a compiled executable) comes later.
- **Electron stays the desktop shell for now** (the owner, CHG-0284): it ships the host's Node and the app's window. Every feature of the desktop main process is either moved out of it or given a web version; none stays Electron-only. As of `apps/desktop/src/main.ts` on 2026-11-14:
  - Moved into the host service: conversation terminals ([0020](0020-terminals-run-in-the-host.md)); app updates; the login shell's `PATH` (`shellPath.ts`), which a host started by a login service needs as much as one started from Finder, or no harness is found; the move of a former data folder (`formerData.ts`), which must run before the first service opens the database; the one-host-per-data-folder lock.
  - Given a web version: the app icon that follows the theme (the Dock and window icon on desktop; the page icon and the installed web app's icon in a browser); opening a link outside the app (the system browser on desktop, a new tab in a browser).
  - How each app is built rather than a feature, adapted per platform: the connection (the window gets the port-and-token file through the preload; the web app pairs through the relay), the app's own title bar beside the macOS window buttons, the guard that keeps the window on the app's own pages, and focusing the running window on a second launch.

## Considered Options

- **A detached process the desktop app leaves running (Paseo's way)**: rejected, because it does not come back after a restart or a crash of its supervisor.
- **Electron kept open in the menu bar with no window**: rejected, because it keeps Electron required.
- **A Unix socket or named pipe**: rejected, because the window cannot open one, so Electron's main process would relay every message.
- **A fixed port and a password the owner sets**: rejected, because every local program can try passwords and the owner has one more secret.
- **The desktop app paired with its own host like any paired device**: rejected for now; one path for every client, but the most work, and its keys still sit in a file.
- **The token in the system keychain**: rejected; three platform implementations, and programs running as the owner can usually read the entry anyway.

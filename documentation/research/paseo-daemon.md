# Paseo daemon: primary-source notes

Researched 2026-11-14. Ideas only; Paseo is Apache 2.0 (`LICENSE` in its repository, and `packages/cli/package.json` says `Apache-2.0`). No code was copied and everything below is in my own words, with short identifiers only.

## Question

The owner asked how Paseo handles running the agent host as its own program, apart from the Electron desktop app, optionally kept running after the desktop app closes, and reachable from browsers and other clients. In particular: runtime and packaging, lifecycle (start, stop, attach, survive quit, login start, crash restart, sleep), how local clients find and authenticate to it, remote access and browser delivery, version compatibility, updates, where terminals run, and which features exist only in the Electron shell.

## Method and sources read

- Source: `https://github.com/getpaseo/paseo`, shallow clone (depth 1) of the default branch, **commit `42c7b7f886ff1395d4d292838daaca9ca929cbda`** (committed 2026-11-14 21:13 +0700, "fix(app): show the Android ripple on sidebar row presses (#9678)"). Package versions at that commit are `0.16.0-beta.2` (`packages/cli/package.json`).
- The clone sat in a new directory under `$TMPDIR`. Nothing in it was run, installed or built; files were only read.
- Primary sources only: source, package manifests, `docs/`, `public-docs/`, `nix/module.nix`, `docker/`. No blog posts or summaries. Paths are relative to the repository root at that commit; line numbers are from that commit.
- I read the daemon's process-ownership code, the desktop's daemon manager and quit logic, the CLI start path, the security and connectivity docs, the terminal worker doc and the compatibility doc. I did **not** read the whole of `bootstrap.ts`, `websocket-server.ts` (3,000+ lines), `session.ts`, the relay service, or the app's host-connection code end to end.

## Findings

### a. Runtime and packaging

- **The daemon is a Node.js process**, not Bun. `docs/architecture.md:26` and `:49` ("A Node.js process"). The CLI entry script runs under `node` (`packages/cli/bin/paseo:1`). The Docker base image is `node:22-bookworm-slim` (`docker/base/Dockerfile:3`) and `.tool-versions` pins Node 22.20.0 for development. I found no `engines` field in the root or server manifest.
- **Inside the desktop app, the same daemon runs on Electron's own Node.** The desktop launches it with `ELECTRON_RUN_AS_NODE=1` (`packages/desktop/src/daemon/node-entrypoint-launcher.ts:26-35`), using the app's own executable; on a packaged Mac it picks the "Helper" binary inside the app bundle (`packages/desktop/src/daemon/runtime-paths.ts:77-99`). The supervisor passes the same variable on to its worker when it detects it (`packages/server/scripts/supervisor-entrypoint.ts:106-109`, `:156-170`). Electron is `44.2.0` (`packages/desktop/package.json:43`); I did not look up which Node version that embeds.
- **Packaging, three routes:**
  1. Inside the desktop app: the `@getpaseo/server` package and its `supervisor-entrypoint.js` sit in the app's asar, with a small runner unpacked beside it (`packages/desktop/src/daemon/runtime-paths.ts:40-49`; `packages/desktop/electron-builder.yml:27-29`).
  2. A separate npm package: `@getpaseo/cli` (`packages/cli/package.json`, `bin: paseo`), which depends on `@getpaseo/server` and has `paseo daemon start|run|stop|restart|status|pair|set-password|config` (`packages/cli/src/commands/daemon/`). `public-docs/updates.md:60` installs it with `npm install -g @getpaseo/cli`.
  3. A container: the official image runs the daemon and the bundled web UI in one container (`public-docs/security.md:110`; `docker/base/Dockerfile`).
  A Nix module also exists (below, b).
- **No single binary.** I found no compiled executable and no `bun build --compile`. The word "bun" appears only in agent-provider code that recognises it as a JavaScript runtime name or a process name (`packages/server/src/server/agent/providers/claude/query.ts:65-70`, `packages/server/src/terminal/terminal.ts:584`, `:597`); it is not Paseo's own runtime or bundler.
- **Three process layers on the host:** a supervisor (holds the PID file), a daemon worker child, and a terminal worker (see g). `packages/server/scripts/supervisor-entrypoint.ts:116-183`; `docs/terminal-worker.md:7-9`.

### b. Lifecycle

- **Start (CLI):** `paseo daemon start` spawns the supervisor **detached**, with stdio ignored, and waits until the PID record shows a listen address (`packages/server/src/server/daemon-instance.ts:272-277`, `:296-333`). `paseo daemon run` is the same path in the foreground, for containers and services (`packages/cli/src/commands/daemon/start.ts:37-55`; `daemon-instance.ts:274`). If a daemon already runs for that home, the start returns it without spawning (`daemon-instance.ts:263-264`; `start.ts:19`, "already_running").
- **Start (desktop):** the app's renderer asks the main process to start the daemon (`packages/app/src/runtime/daemon-start-service.ts`; `packages/desktop/src/daemon/daemon-manager.ts:284-331`). It does **both**: if a daemon already runs it returns that one (attach), otherwise it spawns a detached one in "managed" mode flagged `desktopManaged` (`daemon-manager.ts:296-306`, `:315-326`). It only records "I launched this one" (`ownedLaunch`) when it spawned or acquired the instance itself (`:323-325`).
- **Only a daemon the desktop launched is stopped or restarted by it.** `stopDesktopDaemon` returns without acting unless the instance matches `ownedLaunch`, or a user confirmed that exact PID and start time through the manual path (`daemon-manager.ts:333-366`). The version-mismatch restart also requires desktop ownership (`:271-276`). A daemon started from the CLI is attached and left alone.
- **Setting:** `daemon.manageBuiltInDaemon` (default true) and `daemon.keepRunningAfterQuit` (default **false**) (`packages/desktop/src/settings/desktop-settings.ts:15-16`, `:38-39`). The UI text is "Keep daemon running after quit" / "Daemon keeps running when you quit Paseo" (`packages/app/src/i18n/resources/en.ts:1487-1489`). On quit, the desktop stops its own daemon unless that setting is on, and only if it owns one (`packages/desktop/src/daemon/quit-lifecycle.ts:55-74`; the quit handler holds quit until this finishes, `:118-158`). SIGHUP, SIGINT and SIGTERM to the app also go through this quit path (`:38-53`).
- **Closing the window:** on macOS the app stays alive when the last window closes; on other systems it quits (`packages/desktop/src/main.ts:1068-1072`). So on Linux and Windows, closing the window triggers the quit path above.
- **No login or service integration in the app or CLI.** I searched source, docs and scripts for launchd, LaunchAgent, systemd, `setLoginItemSettings`, `openAtLogin`, a Windows service, `caffeinate`, `powerSaveBlocker` and sleep prevention and found none in the desktop app, CLI or daemon. The only service unit is the **NixOS module** (`nix/module.nix:223-228`, a system service named `paseo` wanted by `multi-user.target`, data dir mode 0700 at `:219-221`). The Docker route relies on the container runtime. The daemon started by the CLI or desktop is a plain detached process; nothing starts it at login.
- **Restart on crash:** the supervisor restarts its **worker** when the worker crashes (`restartOnCrash: true`, `supervisor-entrypoint.ts:149-171`; `packages/server/scripts/supervisor.ts:441-451`) and handles a restart requested over IPC. Nothing restarts the supervisor itself if it dies.
- **Sleep:** I found no power-assertion logic. The only sleep-related items I saw are a stale-lock rule for a VM that resumes (`packages/server/src/server/pid-lock.ts:70-97`) and a desktop compositor watchdog that listens for screen lock and unlock (`packages/desktop/src/window/compositor-watchdog/index.ts:157-158`), which concerns the window, not the daemon. The desktop also exposes system idle time to the renderer (`daemon-manager.ts:502`). What happens to a running daemon during Mac sleep is therefore left to the operating system.

### c. Discovery and authentication for local clients

- **Discovery is by a PID record in the data folder**, `$PASEO_HOME/paseo.pid` (the docs show the config at `~/.paseo/config.json`, `public-docs/connectivity.md:90`). It holds a JSON object: pid, start time, hostname, uid, the listen address once ready, server id, a `desktopManaged` flag and a heartbeat marker (`packages/server/src/server/pid-lock.ts:10-20`). The supervisor writes the listen address after the worker is ready and clears it when the worker exits (`supervisor-entrypoint.ts:173-177`). Clients read it to learn the address (`daemon-instance.ts:51-54`, `:64-91`).
- **One daemon per data folder** is enforced with that file, created exclusively (`open(..., "wx")`, `pid-lock.ts:207`). A second start fails with "Another Paseo daemon is already running" when the recorded owner is alive (`pid-lock.ts:164-182`). A lock is judged abandoned if its process is gone **or** it was written during an earlier boot (`pid-lock.ts:99-110`, with Linux boot id at `:70-97`). The supervisor touches the file every 30 seconds (`pid-lock.ts:46`; `supervisor-entrypoint.ts:128-137`) and shuts down if it loses ownership (`:131-135`). The home directory is made private (`ensurePrivateDirectory`, `pid-lock.ts:4`; directory mode 0700 and file mode 0600, `packages/server/src/server/private-files.ts:6-7`). I did not find an explicit file mode in `pid-lock.ts` itself.
- **Default listen address is TCP `127.0.0.1:6767`** (`packages/server/src/server/persisted-config.ts:385`). The daemon can instead listen on a Unix socket file (`public-docs/security.md:61-63`) and, in desktop code, a named pipe on Windows (`packages/desktop/src/daemon/local-transport.ts:12-15`).
- **Auth for the desktop (and CLI):** by default there is no password; "anyone who can reach the listening address can connect" (`public-docs/security.md:87`). When a password is set, the daemon also writes a random per-start **local credential** file `$PASEO_HOME/local-credential` (32 random bytes, base64url, mode 0600, written to a temporary file then renamed; `packages/server/src/server/local-credential.ts:12-25`, written at `bootstrap.ts:1755` before listening and deleted on stop). Callers who present it bypass the password check (`packages/server/src/server/auth.ts:93-97`, `session-admission-auth.ts:24`). The desktop only hands this credential to its renderer when the running daemon is flagged `desktopManaged` and the requested address equals the one in the PID record (`daemon-manager.ts:480-485`; `local-credential.ts:68-80`). So a CLI-started daemon with a password needs the user to enter that password in the desktop.
- **Local transport:** for local connections the Electron main process opens the WebSocket to the daemon and relays frames to the renderer over IPC (`open_local_daemon_transport`, `daemon-manager.ts:510-520`; `local-transport.ts`). The same Electron-owned bridge carries SSH connections (`docs/architecture.md:129`).

### d. Remote clients

- **Four routes:** direct TCP to a chosen listen address, optionally with a password; an SSH tunnel; a relay; and a reverse proxy in front of the daemon (`public-docs/security.md:19-22`; `public-docs/connectivity.md:11`; `public-docs/web-ui.md:62-68`).
- **Listen address:** `daemon.listen` in `config.json` (`paseo daemon config set daemon.listen 0.0.0.0:6767`), or `PASEO_LISTEN` for deployments (`public-docs/web-ui.md:74-79`; `nix/module.nix:228-231`). It is a startup setting; changing it needs a restart (`connectivity.md:131`).
- **Password:** `paseo daemon set-password` stores a bcrypt hash in `config.json`; every HTTP request needs a bearer header and every WebSocket client sends the password on connect, relay clients inside the encrypted channel; only `/api/health` is exempt (`public-docs/security.md:89-93`). It authenticates but does not encrypt (`:97-98`). Daemon-side DNS-rebinding protection checks the `Host` header against `daemon.hostnames` (`:73-83`).
- **SSH:** uses the local OpenSSH client against an already running daemon; it does not install or start anything remotely, and expects the daemon at `127.0.0.1:6767` on the remote host unless told otherwise (`public-docs/connectivity.md:21-48`; `docs/architecture.md:129`).
- **Relay:** off on new installs; the daemon connects **outbound** and clients meet it there (`public-docs/security.md:26-28`). Pairing hands the client the daemon's public key through a QR code or link; the daemon keeps a persistent keypair in `$PASEO_HOME/daemon-keypair.json` (`security.md:34-35`). The official relay is the Elixir service `getpaseo/paseo-relay` (`security.md:26`). The relay code in this repository lives in `packages/relay`. `docs/relay-endpoint-security.md:14-22` describes a newer "protected" construction (a Noise-style handshake with x25519, ChaCha20-Poly1305) with a legacy NaCl box fallback; once a client has seen a protected handshake with a daemon key it refuses legacy (`:58`).
- **Browser delivery, two sources:** (1) the **daemon can serve the web app itself** from the same HTTP origin; off by default, switched on with `features.webUi.enabled` or `PASEO_WEB_UI_ENABLED`; the web files ship inside the daemon package so UI and daemon versions match (`public-docs/web-ui.md:11`, `:19`, `:23-46`; the build step copies the app's web export into the server package, `scripts/build-daemon-web-ui.mjs:9-13`). The served page connects back to its own origin and needs no "Add host" step (`web-ui.md:58-60`). The static files load without the password so a login screen can show (`web-ui.md:101`). (2) A **hosted web app** at `app.paseo.sh`; pairing links have the form `https://app.paseo.sh/#offer=...` (`packages/app/src/hosts/add-host/internal/pair-link-modal.tsx:222`). The desktop packages the same web export as `app-dist` (`electron-builder.yml:34-35`).
- **End-to-end encryption runs in the client, so in the browser's JavaScript.** The relay secure-channel code is in `packages/relay` and is imported by the shared client package that the app uses (`packages/client/src/daemon-client-relay-e2ee-transport.ts:1-9`; `packages/relay/src/crypto.ts:1-10`, using `tweetnacl`). I did not trace the web bundle, but nothing in the relay path is desktop-only.
- **Several hosts:** the app keeps a list of saved hosts, each with its own connection (`docs/architecture.md:128-129`).

### e. Version compatibility between client and daemon

- **The doc states the policy plainly:** app and daemon ship separately and every combination occurs (`docs/protocol-compatibility.md:3`).
- **Protocol contract:** schema changes must parse both ways; fields are added as optional, never removed or narrowed (`:9-29`). `hello` carries the client protocol version; the daemon accepts the minimum and anything newer, selects the lower of the two maxima and reports it (`:13`).
- **Refusal is narrow.** The daemon rejects a hello only when the client's protocol version is below 1 (`packages/server/src/server/websocket-server.ts:526` constant `WS_PROTOCOL_VERSION = 1`; `:1771-1780`, reason `incompatible_protocol`). The relay path has its own floor (a `4002` close for a client left in legacy mode, `docs/relay-endpoint-security.md:56-64`).
- **Feature contract:** new features are gated by capability flags in `server_info.features`; the app either runs the feature or tells the user to update the host, with no fallback paths (`protocol-compatibility.md:31-41`). One deliberate exception: terminal replay drops apps older than 0.1.81 (`:55-67`).
- Tagged, dated compatibility shims are removed on a schedule (`:126-140`).

### f. Updates

- **Desktop app update:** the app stops its own daemon with reason `app_update` before installing (`daemon-manager.ts:531-539`, `install_app_update`); on startup the daemon it launches is restarted if its version differs from the app's, reason `version_mismatch` (`:297-303`, `:271-276`). Both only apply to a daemon the desktop owns.
- **Terminals survive these two restarts on macOS and Linux** (`keepTerminals`), but not on Windows, where a surviving terminal worker runs the app's executable and would lock the install folder (`daemon-manager.ts:420-432`; the stop uses a lifecycle request rather than SIGTERM, `daemon-instance.ts:111-120`). A daemon too old to support that closes its terminals (`daemon-manager.ts:399-418`).
- **CLI or Docker daemons** update by the user's own means: `npm install -g @getpaseo/cli`, then `paseo daemon restart` (`public-docs/updates.md:60`; `restartDaemon` runs the CLI, `daemon-manager.ts:434-437`). The web UI served by the daemon moves with the daemon package (`web-ui.md:19`).
- **Update channels:** stable and beta; desktop stable releases roll out over 36 hours (`public-docs/updates.md:41-60`).

### g. Terminals

- **PTYs run in a separate terminal worker process, not the daemon and not Electron.** The worker is spawned detached through a short-lived launcher so it leaves the daemon's process tree; it survives daemon restarts, crashes and upgrades, and exits when it has no controller and no terminals (`docs/terminal-worker.md:3`, `:12-15`; `docs/architecture.md:69-70`).
- **The daemon talks to it over a local Unix socket (a named pipe on Windows)** with a per-worker random secret in an owner-only record file; socket and record are mode 0600 inside a 0700 directory (`terminal-worker.md:24-26`). Never more than two workers run, and a worker one protocol version older is adopted to drain (`:37-46`).
- **Folder limits for a remote terminal:** I found a check that the workspace id belongs to an active workspace (`packages/server/src/terminal/terminal-session-controller.ts:612-615`), and the operation needs the `workspace.write` permission (`packages/server/src/server/authorization/operation-permissions.ts:80`). I did not find a check there that the requested `cwd` lies inside that workspace's root; the path-within-root helper is used for filtering lists (`terminal-session-controller.ts:337`, `:545-556`). I did not read the worker's create path. Admission today gives every authenticated client the full owner permission set (`packages/server/src/server/session-admission-auth.ts:18-30`; `OWNER_PERMISSIONS` is all permissions, `authorization/index.ts:23`). The permission model exists, but I saw no per-user limit on what a password-holder may reach.

### h. Desktop-only versus web

- **The Electron bridge is `window.paseoDesktop`** (`packages/desktop/src/preload.ts:32-120`): a generic `invoke`, event subscription, window controls (minimise, maximise, fullscreen, badge count), native dialogs, notifications, opening links and editors, drag-in file paths, menus, a pending "open project" hand-off, and an embedded browser surface with automation.
- **Desktop-only commands** registered in the main process (`daemon-manager.ts:477-523`): daemon status, start, stop and restart, daemon logs, sandbox and updater diagnostics, local credential, local socket and pipe transport, SSH tunnel transport, attachment file storage, app update check and install, CLI shim install, system idle time.
- **Folder picking:** the native directory dialog is the desktop route (`packages/app/src/desktop/pick-directory.ts`); the app's source notes elsewhere that the folder picker for remote hosts is the host-run type-to-search (see [inspirations](../inspirations.md)). I did not re-verify that here.
- **What the browser client gets:** everything that goes over the WebSocket (agents, workspaces, terminals, git, files), including through the relay. It does not get the Electron-owned transports (socket, pipe, SSH), daemon start and stop, the embedded browser, native dialogs, OS notifications through Electron, or update installation. This split is by construction (the preload and `packages/app/src/desktop/` are the only places that call the bridge); I did not enumerate every web-side fallback.

## What this means for Iskios

- Paseo's answer to "its own program" is a Node daemon package that the desktop app bundles and also runs under Electron's Node. It is not a compiled binary and not Bun. The same code ships three ways: inside the app, as an npm CLI, and as a Docker image.
- Its default is that the desktop starts and owns a daemon and stops it on quit; keeping it alive after quit is an off-by-default setting. A daemon the desktop did not launch is attached to, never restarted or stopped by it.
- It does nothing to survive logout, reboot or sleep: no LaunchAgent, no login item, no wake lock. The nearest thing is a NixOS system service and a container. "Background after the app closes" means a detached process that dies with the machine.
- Single-instance is a PID record file with exclusive create, a heartbeat, and a boot check, not a socket lock or a port.
- Local auth is the loopback address plus an optional password; the desktop's bypass is a per-start random token file, honoured only for a daemon it launched.
- Browsers reach it through the daemon's own optional static web server (same origin, version-matched) or a hosted app, with relay encryption done in the client.
- Version handling is a very permissive wire protocol plus per-feature capability flags, and the desktop restarts only its own daemon on a mismatch.
- Terminals in a separate detached worker let the daemon restart without killing shells.

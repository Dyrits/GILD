Problem. Each adapter re-implements process lifetime (close, idle timer, 10 s interrupt grace, untaken-message close), and the restart key has drifted: Claude's ignores model and cwd (claude.ts:301), so a handed-over model would keep a warm --model.

  • Unconfirmed-interrupt path becomes testable
  • Three files fall under 250 lines

2. Harness permission prompts reach Approvals in-process

Strong in-process

codex.ts:157 · opencode.ts:190 · execution.ts:104 (callThreadTool) · rpcProcess.ts:155 · threadToolHandlers.ts:35 · approvals.ts:219

Before: six hops

sequenceDiagram
  participant A as Codex/OpenCode adapter
  participant H as Loopback HTTP + SSE
  participant M as MCP tool handlers
  participant P as Approvals
  A->>H: POST answer_prompt (JSON-RPC)
  H->>M: tools/call
  M->>P: answerPrompt
  P-->>M: allowed / denied
  M-->>H: {"behavior":"allow"} (Claude format)
  H-->>A: SSE data: line, parsed with as

After: one call

sequenceDiagram
  participant A as Codex/OpenCode adapter
  participant P as Approvals
  participant C as Claude Code (MCP)
  A->>P: askOwner(action) via turn request
  P-->>A: allowed / denied + reply
  C->>P: answer_prompt → same capability

Problem. In-process adapters answer their harness's prompts over loopback HTTP in Claude Code's wire format; a failed loopback call becomes a defect in a forked fiber and the turn hangs, and Codex and OpenCode threads see answer_prompt in their tool list.

Solution. The turn request carries an ask-the-owner capability bound to Approvals; MCP answer_prompt stays as Claude's adapter onto it.

  • Locality: one way into prompt policy
  • Typed failure replaces hanging turn
  • Approval tests drop HTTP
  • Claude format stops leaking

3. Domain commands return their follow-ups; one runner applies them

Worth exploring local-substitutable

service.ts · threadToolHandlers.ts · tree.ts · budgets.ts · chatter.ts · deleting.ts · ending.ts · suggestions.ts · lifecycle.ts

Before: duties in the doc comments

service.ts request handler
domain fn · "Callers run it in a transaction" ×50

wake: 6 sites in service.ts, 4 in threadToolHandlers

After

owner request · thread tool (≈1 line each)
Command runner
transaction → publish once after commit → cancel → wake
domain operation returns {storage work, threads to wake, turns to cancel}

Problem. The domain function decides what follows but each caller carries it out by hand; a forgotten wake leaves a thread silently stuck and is testable only through the whole service.

Solution. Operations return their follow-ups; one runner commits, publishes, cancels, and wakes in a fixed order.

  • Locality: commit-notify-wake order in one place
  • Leverage: one runner, ~30 call sites
  • Operations tested by returned follow-ups

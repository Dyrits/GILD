1 · Deepen the thread lifecycle module

Strong in-process · SQLite local-substitutable

lifecycle.ts · threads.ts · tree.ts · ending.ts · deleting.ts · chatter.ts · budgets.ts · approvals.ts · suggestions.ts

Before: 21 state writes in 10 modules

flowchart LR
  ending --> halt[haltThreads]
  deleting --> halt
  chatter --> halt
  budgets --> halt
  halt --> T[(threads.state)]
  budgets -- "SET Stopped, no relax" --> T
  chatter -- "SET Stopped, no relax" --> T
  approvals -- "SET Attention/Running" --> T
  suggestions -- "SET Attention/Running" --> T
  deleting -- "own wake loop" --> wake[wakeWaiting]
  lifecycle --> relax[relaxAncestors]
  deleting --> relax
  linkStyle 4,5,6 stroke:#dc2626,stroke-width:2px;

After: one writer, transitions by name

flowchart LR
  ending --> L
  deleting --> L
  chatter --> L
  budgets --> L
  approvals --> L
  suggestions --> L
  L[[Thread lifecycle]] --> T[(threads.state / blocker)]
  L --> F[turn fibers]
  L --> C[Changes]
  classDef deep fill:#0f172a,color:#f8fafc,stroke:#0f172a,stroke-width:3px;
  class L deep

Problem. haltThreads is shallow. Each caller has to remember the follow-up steps (relax ancestors, cancel, wake), and two Stop paths skip them: Stop at a budget, and Stop both on chatter.

Solution. The lifecycle module becomes the only writer of a thread's state and blocker. Callers name a transition (stop, hold for a reason, release, end a turn), and the module runs every follow-up step in a fixed order.

  • Locality: state bugs concentrate in one module
  • Leverage: one call per transition, many callers
  • Fixes the review's finding P1 by construction
  • Tests: one transition table through one interface

Problem. The glossary defines Attention as one concept, but the code implements it five separate times. Approvals and suggestions copy each other line for line, and the rule for which holds Stop withdraws only shows up in tests.

Solution. One Attention module owns the hold reasons, the waiting Deferreds, withdrawal by cause, and startup recovery. Approvals and suggestions keep only their own policy.

  • Locality: a new hold kind is one edit
  • Absorbs standards finding S7 (deferred)
  • Tests: one "withdrawn or kept on Stop, Interrupt, restart" suite

  classDef deep fill:#0f172a,color:#f8fafc,stroke-width:3px;

Problem. Messages are inserted in three places, each with its own sequence rule, and the "pending messages" query is pasted twice. messaging.ts (61 lines) is shallow, while threads.ts has grown to 438 lines.

Solution. The messaging module owns appending, pending, steer or queue, delivered or undelivered, and mission activity.

  • Locality: delivery rules (CHG-0039) in one place
  • Shrinks threads.ts below the size rule
  • Tests: delivery checked without running turns

4 · Thread tools: one definition per tool, transport apart

Worth exploring in-process · loopback HTTP local-substitutable

After

Thread tool catalogue

one schema → listing, decoder, allowed list · typed handlers

MCP transport (JSON-RPC, SSE)

Problem. Nothing keeps a tool's four descriptions in sync, and Suggestions takes raw MCP args: unknown, so the MCP argument shape leaks into a domain module.

Solution. Each tool is one unit generated from one schema, and the transport is a separate module. Keeps ADR 0005.

  • Locality: a new tool is one place
  • Tests: tool behavior without HTTP

Problem. The app works out the service's rules again from raw state and blocker, and those rules are untested in the app. The future phone app would have to copy them a third time.

Solution. The thread detail carries the actions available now and the hold reason, computed by candidates 1 and 2. In line with ADR 0002 and 0009.

  • Leverage: desktop and phone share the rules
  • Tests: through ReadMission in the service suite

6 · Remove the Waker indirection

Speculative in-process

waker.ts · threads.ts · mcp.ts · suggestions.ts · service.ts

Before: cycle broken by a Ref

flowchart LR
  Threads -->|urlFor| ToolServer
  ToolServer --> Waker
  Waker -.Ref registered later.-> Threads
  linkStyle 2 stroke:#dc2626,stroke-width:2px;

After

flowchart LR
  Threads --> Endpoints
  ToolServer --> Endpoints
  ToolServer --> Threads

Problem. Waker has only one adapter and exists only to break a dependency cycle. A call made before registration silently does nothing.

Solution. Pull endpoint issuing out into its own small module, so the tool server can depend on Threads directly. Keeps ADR 0010.

  • Honest dependency graph
  • One silent failure mode gone

Top recommendation

1 · Deepen the thread lifecycle module, then 2 · Attention

The duplication and the real bugs are in state changes: two Stop paths leave a Waiting parent stuck. These are also the most-changed modules, and candidates 2 and 5 build on candidate 1's interface. No ADR is touched.

Problem. "Is this thread sandboxed, and does this action stay inside?" is answered in four places that already disagree: Claude Code reports Sandboxed whenever the host can sandbox, yet isSandboxedOf sandboxes only at RiskyOnly; Codex reports Sandboxed and flags every request as outside it (finding P5); OpenCode checks unasked edits against the raw request.cwd while Approvals checks editFolderOf; the folder check is skipped without an OpenCode sandbox (P6).

Solution. Adapters report only facts; one Containment module turns them into the decision; Approvals only asks, records and remembers.

  • Locality: P4, P5, P6 and any new harness land in one module
  • Leverage: three adapters and Approvals share one answer
  • Interface is the test surface: a table of harness × level × sandbox × action, no process
  • approvals.test.ts and the harnesses.test.ts ask cases survive end to end
  • OpenCode isUnaskedEdit assertions collapse into the table

Problem. deriveAction returns null "when the tool's own checks will refuse it", so each check lives in the derivation and in the tool body, and each body must remember consumeReceipt before it writes; nothing enforces that. create_realm already matches realms two ways: by resolved real path in the derivation, by findRealmOfAnyKind(name) in the tool.

Top recommendation

The release's safety guarantee is sandbox-first autonomy (CHG-0208), and open findings P4, P5 and P6 sit in exactly this code; the Claude Code disagreement is a live wording bug at the stricter approval level. Fixing them in one module costs less than patching four places.

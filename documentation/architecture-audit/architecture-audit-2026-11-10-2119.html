Problem. Eighty-six files share one directory, so locating the harness adapters or the lore store means scanning every name, and the file names carry the grouping as prefixes (lore*, harness*) that a folder would carry itself.

Solution. Move each cluster that nothing else leans into its own folder, with an index.ts as that module’s interface; core holds the shared base (errors, changes, settings, store), and the 37 files that call each other stay together in one folder until they are separated by their own deepening.

  • Interface per folder: index.ts is the seam
  • Locality: lore changes stay in lore/
  • Folder edges point one way into core
  • 12 back-edges named, each a real seam decision
  • Tests reach a folder through its interface
  • architecture.md already groups files by these names
Capability-named folders such as threads/, quests/, tools/ do not work yet: the hub has 13 imports from threads into quests and 20 back, so those folders would only look separate. The 12 dashed edges are the real work: the MCP server description that the three adapters import (mcp.ts), lore’s reads of the journal and tool catalogue, and the budget modules’ calls into commands and lifecycle.

Problem. Tests import single files (../src/loreStore.ts, ../src/threadTools.ts), so they test past a folder’s interface and break on every internal rename.

Solution. When a folder gets an index.ts, tests that can reach their subject through it do; the rest stay on the internal file, which marks where the interface is too narrow.

  • Interface is the test surface
  • Moves become import-path edits only
  • Narrow interfaces show up as tests that cannot use them

Leave flat

  • packages/contracts/src (17 files): one file per record family behind one index.ts; the deletion test says a folder would add a level and no locality.
  • apps/desktop/src (7 files): small, each file one Electron concern.

What a move costs here

  • documentation/architecture.md and the capability specifications name files by bare name (about 150 backticked file names across the documents); every moved file needs those references updated, or a pass that rewrites them to folder paths.
  • Git history follows renames, but the hot-spot list above (conversation.tsx, service.ts, store.ts) starts a new path; do the moves as one commit with no edits to content so git log --follow stays clean.
  • packages/service/package.json exports only ./src/index.ts, so no consumer outside the package changes; apps/desktop and the app import through @gild/service and @gild/contracts.
  • No decision record contradicts this: folder layout is reversible, so a rule in documentation/conventions.md fits better than an ADR. The existing rule (“a file is split by responsibility past about 250 lines”) is what grew the flat list, and it needs a companion about where split files go.

Outcome · applied 2026-11-10 (CHG-0125)

  • Candidate 1 applied. core/, harness/, lore/, policy/ and work/, each but work/ with an index.ts. Deviations from the diagram: the spend folder was dropped (the budget modules call commands and lifecycle, so they stay in work/; spending moved to core/), and the 12 back-edges were resolved by moving tokensOf, wordsOf and ToolAnswer down to core/, loreTools up to work/, and giving ThreadAccess an unaskedTools field so Claude Code's arguments no longer import the tool server. No folder imports work/ now.
  • Candidate 2 not applied, as advised.
  • Candidate 3 applied with a different cut from the diagram: the audit counted 5 back-edges, but the graph also had screen-level rings, so the folders are foundation, attachments, terminal, ui, editors, crest, realms, rituals, quests, lore, conversation, settings, shell, in one downward chain with no cycles. The shell's context hooks moved to foundation/shellContext.tsx. No index.ts per app folder: React components import each other directly and a barrel there is a second place to keep in step.
  • Candidate 4 applied: tests mirror the folders; 188 imports go through the new interfaces and 8 test imports stay on an internal file.
  • The note on documentation cost was smaller than stated: file names did not change, so the roughly 150 bare file names in the documents still find their file; only 5 path references needed an edit.
Top recommendation

Candidate 1: the service’s leaf folders, then candidate 3 for the app

The service is the largest directory, its clusters (harness, lore) are already how architecture.md describes it, and the graph shows exactly which 12 edges to fix; settle those, move, and the same procedure carries to the app.
